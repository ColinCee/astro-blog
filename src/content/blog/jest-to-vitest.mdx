Above is our sim tests, 7 minutes on Jest and 23 seconds after moving to Vitest.[^how]

Contrary to popular belief, Vitest isn't purely quicker, in fact it was actually slower than Jest with the defaults. The speed came from a config option to do with isolation but it has its own caveats.

## What are sim tests?

At EDF we have this concept of sim tests. Given some input for an account, we play it through our rules engine and it produces a snapshot of what the events would be per day. These are events that actually get emitted into EventBridge, and other services ingest them from there.

A sim's snapshot is just the events per day, so a six-day one looks something like this, trimmed down:

```json title="one sim's snapshot"
{
  "steps": {
    "0": { "events": [
      { "type": "EVENT_A" },
      { "type": "EVENT_B" }
    ] },
    "1-4": { "events": [] },
    "5": { "events": [
      { "type": "EVENT_C" }
    ] }
  }
}
```

Days with nothing in them collapse into one entry, like the `"1-4"` there. So fundamentally it's a state machine simulator, from a start date to an end date. There's over 1,000 of them and each one is a test file that imports the engine.

## Why did it take 7 minutes?

Originally the sims ran in a JavaScript script that kind of duplicated what Jest already does, but in a janky homemade solution that loops over all the sim files and runs them. So we moved them onto Jest because it's the standard runner and to be honest it should've been that way from the start.

After profiling turns out most of the time was spent importing because each test gets its own isolated copy of modules. For the nitty gritty see [how Jest and Vitest run a file](#internals).

## The config option

Vitest has the same isolation by default but the difference is that it lets you turn it off.

```ts title="vitest.simulations.config.ts"
export default defineConfig({
  test: {
    // engine loads once per worker, not once per file
    isolate: false,
    // fail any file that depends on another's leftovers
    sequence: { shuffle: true },
  },
});
```

What this does is a worker keeps its modules between files, so the engine loads once per worker instead of once per file.

Jest and plain Vitest both go up with every file because every file loads the engine again, and plain Vitest is actually worse. The `isolate: false` line is basically flat, going from 98 files to 1,371 only added 14 seconds.

## Limitations

- A test that mutates something it imported now leaks into later files, so shuffle the files to catch it.

<details class="more" id="internals">
<summary>How Jest and Vitest run a file</summary>

**Jest.** Each test file runs in its own Node `vm` context, which is basically a separate JavaScript realm with its own globals and its own `Array` and `Object`. Jest's runtime provides the `require` inside it and keeps a module table per context, which is why mocks can't leak between files, and also why `x instanceof Array` is sometimes false under Jest, [that one's been open since 2017](https://github.com/jestjs/jest/issues/2549). `--runInBand` gets rid of the worker processes but each file still gets its own context and reloads everything.

**Vitest.** The files go to a pool of workers, the default is `forks` which is a child process per file, `threads` is a worker thread per file, and the `vm*` pools behave like Jest and can't turn isolation off. With `isolate: false` on `forks` or `threads` the worker stays alive and keeps its module cache.
