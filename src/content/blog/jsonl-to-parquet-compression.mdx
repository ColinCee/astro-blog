At EDF I pull data-lake exports down from S3 most days to debug production issues. Each one is a JSONL file of about 4.5GB, around 1.5 million records, and it takes over ten minutes to download.

So I tried converting one to Parquet:

<Fig caption="Same 1.5 million records, drawn to scale. 95% smaller.">
  <Cmp
    rows={[
      { label: "data_export.jsonl", value: 4500, text: "4.5 GB" },
      { label: "data_export.parquet", value: 221, text: "221 MB", after: true },
    ]}
  />
</Fig>

It's the same records, and the download went from ten minutes to about 30 seconds. I wanted to know where all that space actually went, so I had a look.

## Where does 4.5GB go?

JSONL is just one JSON object per line, so every line writes out every field name. We have 106 fields, so that's 106 keys repeated 1.5 million times, which comes to roughly 1.9GB of nothing but keys.

On top of that everything is text. A boolean is the string `"TRUE"` when it could be one bit, a timestamp is a full ISO string when it could be 8 bytes, and `"null"` gets spelled out millions of times. Add up the keys, quotes, colons and commas and about 66% of the file is overhead.

But stripping all that only gets you to about 1.5GB, which is 3× smaller. Parquet gets another 7× out of the data itself, and that part is down to it storing data by column.

## So what does storing by column do?

JSONL writes a whole record, then the next record. Parquet takes all the values for one field and writes them next to each other, then does the next field. Here's a made-up example with 8 records, where each square is one byte:

<Fig caption="Parquet's own headers are left out, they only matter for tiny files like this one.">
  <Bytes
    records={[
      { id: 1, status: "OPEN", active: true },
      { id: 2, status: "OPEN", active: true },
      { id: 3, status: "OPEN", active: true },
      { id: 4, status: "OPEN", active: true },
      { id: 5, status: "DONE", active: false },
      { id: 6, status: "DONE", active: false },
      { id: 7, status: "DONE", active: false },
      { id: 8, status: "OPEN", active: true },
    ]}
  />
</Fig>

Because a column is all one type, Parquet can store it at its real size, so a number is 4 bytes and a boolean is one bit. And because the repeated values now sit next to each other, it can use dictionary encoding, which means writing each distinct value once and then just storing which one each row has. Our real `status` field only has 6 possible values, so that's 3 bits a row instead of a string.

<Fig title="The status column from that example">
  <Encode
    steps={[
      { label: "In JSONL", show: "\"status\":\"OPEN\",\"status\":\"OPEN\",\"status\":\"OPEN\",…", bytes: 128 },
      { label: "As a column", show: "OPEN OPEN OPEN OPEN DONE DONE DONE OPEN", bytes: 32 },
      { label: "Dictionary encoded", show: "OPEN DONE + 0 0 0 0 1 1 1 0", bytes: 9 },

  />
</Fig>

Last of all it runs Zstandard compression over each column. Compression works by finding repeats, and a column of similar values has way more of them than rows of mixed fields do.

## Any downsides?

The one downside is that you can't `grep` a Parquet file. But `duckdb -c "SELECT * FROM 'file.parquet'"` opens it instantly, so I haven't really missed that.
