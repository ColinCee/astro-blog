At EDF I pull data-lake exports down from S3 most days to debug production issues. Each one is a JSONL file of about 4.5GB, around 1.5 million records, and it takes over ten minutes to download.

So I tried converting one to Parquet:

<Fig caption="Same 1.5 million records, drawn to scale. 95% smaller.">
  <Cmp
    rows={[
      { label: "data_export.jsonl", value: 4500, text: "4.5 GB" },
      { label: "data_export.parquet", value: 221, text: "221 MB", after: true },
    ]}
  />
</Fig>

It's the same records, and the download went from ten minutes to about 30 seconds. I wanted to know where all that space actually went, but I can't share our data, so I made a fake export the same shape with [a DuckDB script](/blog/jsonl-to-parquet-compression/make-data.sql): 1.5 million records and 106 fields. I had to guess what the fields look like, so it's not exact. The first line starts like this:

```json
{"id":0,"uuid_ref_1":"bf48c54f-7117-2ebc-cb28-919e5a62668d","uuid_ref_2":"93c74525-2f0a-c090-4542-9febfd0eafa8","uuid_ref_3":"fdfee444-b56b-b291-e6b1-69dad989e61e","uuid_ref_4":"24e40cc5-d528-1ee6-cf8f-f6b5a484f845","uuid_ref_5":"c40a7e52-9e5e-922c-f13a-6298ab15c787","timestamp_01":"2025-01-01 00:00:07","timestamp_02":"2025-01-17 14:00:19",…
```

The [first 100 lines](/blog/jsonl-to-parquet-compression/sample.jsonl) are there if you want a proper look, and every number below comes from [this script](/blog/jsonl-to-parquet-compression/measure.sql).

## Where does 4.0GB go?

JSONL is just one JSON object per line, so every line writes out every field name. With 106 fields that's 106 keys repeated 1.5 million times, which comes to 2.0GB of nothing but keys.

On top of that everything is text. A boolean is the string `"TRUE"` when it could be one bit, a timestamp is a full date and time string when it could be 8 bytes, and `null` gets spelled out millions of times. Add up the keys, quotes, colons and commas and 66% of the file is overhead.

But stripping all that only gets you to 1.4GB, which is 3× smaller. Parquet gets another 3× out of the data itself, and that part comes from how it stores each column.

## So what does storing by column do?

JSONL writes a whole record, then the next record. Parquet takes all the values for one field and writes them next to each other, then does the next field. Here's the first 5 rows with 3 of the fields:

<Fig caption="The sizes are for the whole file, the names once and the values as text, before any encoding. Tap a tab to stop it.">
  <Morph
    sizes={["4.0 GB", "1.4 GB"]}
    records={[
      { id: 0, status: "CLOSED", currency: "GBP" },
      { id: 1, status: "ACTIVE", currency: "GBP" },
      { id: 2, status: "ACTIVE", currency: "GBP" },
      { id: 3, status: "REVIEW", currency: "GBP" },
      { id: 4, status: "ACTIVE", currency: "GBP" },
    ]}
  />
</Fig>

Because a column is all one type, Parquet can store it at its real size, so a number is 8 bytes and a boolean is one bit. And because the repeated values now sit next to each other, it can use dictionary encoding, which means writing each distinct value once and then just storing which one each row has.

<Fig title="The status column" caption="The first 5 rows. The sizes are for all 1.5 million.">
  <Lookup
    name="status"
    sizes={["9.7 MB", "570 KB"]}
    values={["CLOSED", "ACTIVE", "ACTIVE", "REVIEW", "ACTIVE"]}
  />
</Fig>

Our `status` field only has 6 possible values, so that's 3 bits a row instead of a whole string.

Last of all it runs Zstandard compression over each column. Compression works by spotting bytes it's already seen and writing "copy those again" instead, so it does best where the same values sit next to each other, like a currency that's nearly always GBP.

<Fig title="Zstandard on the currency column" caption="The first 5 rows, and the simplest version of the idea.">
  <Repeats values={["GBP", "GBP", "GBP", "GBP", "GBP"]} />
</Fig>

Parquet on its own is about 4× smaller than the JSONL, and Zstandard halves it again. That's 9× on the fake file, against 20× on our real one, so my guess at the fields is clearly off somewhere. Zstandard on the JSONL by itself does pretty well too, but Parquet with it is still smaller, and you can actually query it.

## Any downsides?

The one downside is that you can't `grep` a Parquet file. But `duckdb -c "SELECT * FROM 'file.parquet'"` opens it instantly, so I haven't really missed that.
