At EDF I pull data-lake exports down from S3 most days to debug production issues. Each one is a JSONL file of about 4.5GB, around 1.5 million records, and it takes over ten minutes to download.

So I tried converting one to Parquet:

<Fig caption="Same 1.5 million records, drawn to scale. 95% smaller.">
  <Cmp
    rows={[
      { label: "data_export.jsonl", value: 4500, text: "4.5 GB" },
      { label: "data_export.parquet", value: 221, text: "221 MB", after: true },
    ]}
  />
</Fig>

It's the same records, and the download went from ten minutes to about 30 seconds. I wanted to know where all that space actually went, so I had a look.

## Where does 4.5GB go?

JSONL is just one JSON object per line, so every line writes out every field name. We have 106 fields, so that's 106 keys repeated 1.5 million times, which comes to roughly 1.9GB of nothing but keys.

On top of that everything is text. A boolean is the string `"TRUE"` when it could be one bit, a timestamp is a full ISO string when it could be 8 bytes, and `"null"` gets spelled out millions of times. Add up the keys, quotes, colons and commas and about 66% of the file is overhead.

<Fig title="Where the 4.5 GB went" caption="The split between field names and other syntax is approximate.">
  <Cmp

But stripping all that only gets you to about 1.5GB, which is 3× smaller. Parquet gets another 7× out of the data itself, and that part comes from how it stores each column.

## So what does storing by column do?

JSONL writes a whole record, then the next record. Parquet takes all the values for one field and writes them next to each other, then does the next field. Here's a made-up example with 5 records:

<Fig caption="Bytes before any encoding: the names once and the values as text. Tap a tab to stop it.">
  <Morph
    records={[
      { id: 1, status: "OPEN", active: true },
      { id: 2, status: "OPEN", active: true },
      { id: 3, status: "OPEN", active: true },
      { id: 4, status: "OPEN", active: true },
      { id: 5, status: "DONE", active: false },
    ]}
  />
</Fig>

Because a column is all one type, Parquet can store it at its real size, so a small number is 4 bytes and a boolean is one bit. And because the repeated values now sit next to each other, it can use dictionary encoding, which means writing each distinct value once and then just storing which one each row has.

<Fig title="The status column from that example">
  <Lookup name="status" values={["OPEN", "OPEN", "OPEN", "OPEN", "DONE"]} />
</Fig>

Our real `status` field only has 6 possible values, so that's 3 bits a row instead of a whole string.

Last of all it runs Zstandard compression over each column. Compression works by spotting bytes it's already seen and writing "copy those again" instead, so a column where the same values sit next to each other is pretty much ideal.

<Fig title="Zstandard on the status column" caption="The simplest version of the idea, on the plain text.">
  <Repeats values={["OPEN", "OPEN", "OPEN", "OPEN", "DONE"]} />
</Fig>

So putting it all together, here's what those 5 records end up as:

<Fig title="The example, encoded" caption="Zstandard is left out, 5 records is too little for it to find much. Parquet's own headers are left out too.">

      { id: 4, status: "OPEN", active: true },
      { id: 5, status: "DONE", active: false },
    ]}
  />
</Fig>

## What about something bigger?

5 records is a bit small to see Zstandard do anything, so I made up 1.5 million records shaped like our export and wrote them out each way. The first few lines look like this:

```json
{"id":0,"account_id":"ACC-149440","status":"ACTIVE","active":"TRUE","flagged":"FALSE","created_at":"2025-01-01 00:00:11","amount":200.3,"currency":"GBP","region":"South","channel":"post","note":null,"external_ref":null}
{"id":1,"account_id":"ACC-134724","status":"ACTIVE","active":"TRUE","flagged":"TRUE","created_at":"2025-01-01 00:00:35","amount":231.47,"currency":"GBP","region":"West","channel":"app","note":"manual check 624","external_ref":null}
{"id":2,"account_id":"ACC-120781","status":"PENDING","active":"TRUE","flagged":"FALSE","created_at":"2025-01-01 00:00:54","amount":414.92,"currency":"GBP","region":"South","channel":"phone","note":null,"external_ref":null}
```

They come from [a few lines of DuckDB](/blog/jsonl-to-parquet-compression/make-data.sql), and [the first 1,000 lines](/blog/jsonl-to-parquet-compression/sample.jsonl) are there too if you want a look.

Parquet on its own is already about 5× smaller than the JSONL, and Zstandard takes it down another 3×. Zstandard on the JSONL by itself does pretty well too, but Parquet with it is still about half the size, and you can actually query it.

The ids just count up and nearly everything is GBP, so there's loads for it to find, but status, channel and region are random picks in this data so there's not much. All together that's about 18× on the made-up data, and on our real file it's what takes 4.5GB down to 221MB.

## Any downsides?

The one downside is that you can't `grep` a Parquet file. But `duckdb -c "SELECT * FROM 'file.parquet'"` opens it instantly, so I haven't really missed that.
