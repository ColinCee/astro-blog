At EDF I pull data-lake exports down from S3 most days to debug production issues. Each one is a JSONL file of about 4.5GB, around 1.5 million records, and it takes over ten minutes to download.

So I tried converting one to Parquet:

<Fig caption="Same 1.5 million records, drawn to scale. 95% smaller.">
  <Cmp
    rows={[
      { label: "data_export.jsonl", value: 4500, text: "4.5 GB" },
      { label: "data_export.parquet", value: 221, text: "221 MB", after: true },
    ]}
  />
</Fig>

It's the same records, and the download went from ten minutes to about 30 seconds. 

Since I can't share real data, I made a fake export with a different shape using [a DuckDB script](/blog/jsonl-to-parquet-compression/make-data.sql): 1.5 million records and 106 fields. The first line starts like this:

```json wrap
{
  "id": 0,
  "uuid_ref_1": "bf48c54f-7117-2ebc-cb28-919e5a62668d",
  "timestamp_01": "2025-01-01 00:00:07",
  "status": "CLOSED",
  "currency": "GBP",
  "is_flag_01": "FALSE",
  "amount_01": 555.21,
  "text_ref_01": "REF-39424920-C54",
  "optional_01": null,
  …
}
```

The [first 100 lines](/blog/jsonl-to-parquet-compression/sample.jsonl) are there if you want a proper look, and every number below comes from [this script](/blog/jsonl-to-parquet-compression/measure.sql).

## Where does 4.0GB go?

JSONL is just one JSON object per line, so every line writes out every field name. With 106 fields that's 106 keys repeated 1.5 million times, which comes to `2.0GB` of nothing but keys.

On top of that everything is text. A boolean is the string `"TRUE"` when it could be one bit, a timestamp is a full date and time string when it could be 8 bytes, and `null` gets spelled out millions of times. Add up the keys, quotes, colons and commas and 66% of the file is overhead.

In this dummy example we can see the actual data is 1.4GB, but Parquet can reduce that even further with encoding and compression.

## So what does storing by column do?

JSONL writes a whole record, then the next record. Parquet takes all the values for one field and writes them next to each other, then does the next field. Here are the first 5 rows with 3 of the fields:

<Fig caption="The first 5 rows and 3 of the fields. By column is the names once and the values as text. Tap a tab to stop it.">

      { id: 3, status: "REVIEW", currency: "GBP" },
      { id: 4, status: "ACTIVE", currency: "GBP" },

  />
  <p class="fig__k">The whole file</p>
  <Cmp
    max={4030.6}
    cols={["10.5rem", "7.5rem"]}
    rows={[
      { label: "JSONL", value: 4030.6, text: "4.0 GB" },
      { label: "By column", value: 1375.3, text: "1.4 GB · −66%", after: true },
    ]}
  />
</Fig>

Because a column is all one type, Parquet can store it at its real size, so a timestamp is 8 bytes instead of 19 characters and a boolean is one bit. And because the repeated values now sit next to each other, it can use dictionary encoding, which means writing each distinct value once and then just storing which one each row has.

<Fig title="The status column" caption="The first 5 rows. The status sizes are for all 1.5 million.">
  <Lookup
    name="status"
    sizes={["9.7 MB", "570 KB"]}
    values={["CLOSED", "ACTIVE", "ACTIVE", "REVIEW", "ACTIVE"]}
  />
  <p class="fig__k">The whole file</p>
  <Cmp
    max={4030.6}
    cols={["10.5rem", "7.5rem"]}
    rows={[
      { label: "By column", value: 1375.3, text: "1.4 GB" },
      { label: "Encoded", value: 934.8, text: "935 MB · −32%", after: true },
    ]}
  />
</Fig>

Our `status` field only has 6 possible values, so that's 3 bits a row instead of a whole string.

Last of all it runs Zstandard compression over each column. Compression works by spotting bytes it's already seen and writing "copy those again" instead, then writing the most common bytes in fewer bits. The first part does best where the same values sit next to each other, like a currency that's nearly always GBP.

<Fig title="Zstandard on the currency column" caption="The first 5 rows, and the simplest version of the idea.">

## Any downsides?

The one downside is that you can't `grep` a Parquet file. But `duckdb -c "SELECT * FROM 'file.parquet'"` opens it instantly, so I haven't really missed that.
